Cyber-physical simulation · RTX 5090

A blister line that inspects and rejects itself, in simulation.

A single-process digital twin of a pharmaceutical blister packaging cell runs the whole control loop against synthetic physics: a strobe exposure is rendered at the inspection station, handed to a TensorRT FP16 detector over a zero-copy CUDA DLPack pointer, turned into a PASS/REJECT verdict against calibrated thresholds, clocked forward through an encoder shift register, and actuated as a pneumatic kick that PhysX then confirms by overlap query — with every pack written to an append-only audit ledger. The model was trained entirely on synthetic data generated from the same asset, and its verdicts match the previous baseline pack for pack.

Asset realism

v1 was a CAD shape. v2 is a part.

Textures do not load on this ovrtx build, so every piece of micro-detail in v2 is real geometry with per-vertex normals — which is also why the detector can see it. Drag the divider, or focus it and use the arrow keys.

Asset v1 — faceted CAD Asset v2 — procedural lathe profiles

Both images are rendered through /Render/Camera at the identical pose; the crops use the identical box (330,190)–(950,530).

  • Biconvex tablets. 8 mm lathe meshes with a curved face that catches a central highlight, replacing v1’s flat-topped cylinders.
  • Knurled waffle seal. 1.25 mm pitch at 80 µm depth, carried across the whole card face as geometry.
  • OmniGlass PVC domes. Index of refraction 1.53, smooth and circular — v1’s domes were faceted octagons.
  • Rounded, chamfered card. 3 mm corner radius and a 0.3 mm chamfer on a 90 × 45 mm, 1.5 mm card and foil.
  • Coaxial ring light. A DiskLight at 2000 nominal, randomised 0.5–1.5× through the synthetic data generator; v1 had only a dome and a key light.
  • Ten cavities, two rows of five. 12 mm pockets, 16 mm pitch along the belt and 11 mm across it.
Constraint that shaped the asset: textures do not load on this ovrtx build. Anything that had to be visible to the detector — the knurl, the dome curvature, the tablet crown — had to be modelled, not painted. The v1 pack’s confidences ran 0.21–0.55; the v2 run reads 0.9x.

Picture-in-picture logic

On a REJECT the HUD cuts a 2× magnified crop around the highest-confidence defect box and draws it in a red-cased panel headed DEFECT 2×; where the reason is under-occupancy and the missing tablet produced no defect box of its own, the crop is taken at the grid-expected cavity instead, so the operator is always shown the cavity that caused the verdict rather than a blank corner of the pack. On a PASS the same panel is replaced by the green NOMINAL badge with one dot per satisfied cavity. The inset is drawn from the same detection list that produced the verdict — it is a view of the decision, not a second one.

Dual-chute material handling

Two destinations, one rigid-body budget

A 1.3 mm thin box travelling at roughly 3 m/s is exactly the case that makes a discrete solver explode or tunnel. The handling path is built so that it cannot: every static surface is a 30 mm thick invisible collider, and the outfeed is never allowed to hold the body pool.

  1. 1 — Belt collider end, x = 0.60 m. Past the nose roller an accepted pack stops being re-driven and becomes a free rigid body. On-belt packs are re-driven to (1.6, 0, 0) m/s on every 240 Hz step against a zero-friction belt material.
  2. 2 — Ramp lip, x = 0.62 m, 6 mm below the belt top. The 20 mm gap and the 6 mm drop are deliberate: the pack must clear the roller before it touches anything.
  3. 3 — Ballistic flight, about 11 cm. No contact at all between the belt and the ramp, so there is no grazing contact for the solver to resolve at the transition.
  4. 4 — First contact at x ≈ 0.73 m. From there the pack is in sliding contact down the ramp; ramp friction is 0.30 static / 0.25 dynamic, restitution 0.05.
  5. 5 — 10° × 0.20 m stainless ramp. Steeper trials at 12–16° overflew the tote; 10° keeps the slide inside it. The collider behind the visible surface is a 30 mm thick invisible static box.
  6. 6 — Stacking tote. Inner 240 × 250 mm, 120 mm walls, floor at z = −0.22 m, friction 0.60 / 0.50. Walls and floor are 30 mm thick invisible boxes for the same reason as the ramp.

Accept side Rolling FIFO and the pool budget

The outfeed keeps five settled packs. When a sixth settles, the oldest — the bottom of the stack — is recycled straight back into the body pool. That cap is what stops the outfeed from quietly consuming the simulation: the pool of 16 is budgeted as 6 on the belt, 2 in reject transit and 1 spare held in reserve, leaving at most 7 outfeed bodies. A pack is called settled when |v| < 0.05 m/s and |ω| < 1 rad/s hold for 24 consecutive steps (0.1 s), with a 2 s dwell fallback so nothing can wedge the queue forever.

Traceability

21 CFR Part 11-style audit trail

One record is written at the moment of actuation for every pack, and flushed before the next step runs. These are the last three lines of the local ledger, verbatim.

Loading record…

showcase/media/audit_sample.jsonl — the last 3 lines of reports/audit_trail.jsonl, which held 1,416 records at v1.0.0.

  • Append-only JSONLOne object per line, never rewritten, never reordered. The twin appends its PhysX confirmations to the same file under the same lock, which is why records for two different packs can interleave.
  • fsync per recordEach line is flushed to the device before the controller returns, so a record exists on disk before the actuator is allowed to fire.
  • Two schemasblister.audit/1 for the verdict and actuation, blister.confirm/1 for the PhysX bin-overlap confirmation, carrying the landing coordinates and the sim time.
  • Engine SHA-256 pinnedThe hash of the TensorRT engine binary (c06db0d3…4078d) is written into every audit record and into thresholds.json, so a verdict can always be tied back to the exact model that produced it.
  • Run, host and UTC timerun_id, controller_version, host and an ISO-8601 UTC timestamp on every line.
  • Encoder ticks at trigger and actionThe pack’s position in encoder counts when it was photographed and when it was acted on — 0.5 mm per tick — which is what makes the delay auditable rather than assumed.
  • Fail-closed on late verdictsThe inference budget is 25 ms. A verdict that arrives late is not trusted: the pack is rejected and the record carries late_verdict.
  • Not hash-chainedThe SHA-256 in each record identifies the model binary, not the previous record. There is no record-to-record chaining, and this page does not claim any.

Reproduction

The whole chain, end to end

Windows 11, RTX 5090 (32 GB), Python 3.12 via uv; torch 2.10+cu130, TensorRT 11.3, ultralytics 8.4.146, ovrtx 0.4.1 / ovstage 0.1.1 / ovphysx 0.5.11 in a single process (Isaac Sim is not used), opencv 5.0.

shell·uv
# environment
uv sync

# asset and synthetic data
uv run python src/simulation/assets/blister_factory.py --render-check
uv run python src/simulation/sdg_pipeline.py --frames 2400

# train, export, calibrate
uv run python src/training/train.py --name yolo11n_v2 --epochs 30 --sweep-batches 32,64,128
uv run python src/export/export_engine.py --best models/runs/yolo11n_v2/weights/best.pt
uv run python src/inference/calibrate_thresholds.py --margin 0.05

# gates
uv run python src/inference/drift_check.py --frames 50
uv run python src/inference/controller.py --test

# the twin
uv run python src/simulation/live_factory_twin.py --demo --packs 20 --pool 16 --lockstep --record-video
uv run python src/simulation/live_factory_twin.py --demo --packs 30 --pool 16 --lockstep

# parity audit and the full verification sweep
uv run python scripts/parity_v2.py
bash scripts/final_v3.sh

controller.py --test is the controller self-test: 20 validation frames on a simulated 1.6 m/s belt with injected faults. Not committed to the repository, and regenerated by the commands above: data/ (2,400 frames), the model weights, the ONNX graph and the TensorRT engines. The yolo11n.pt base weights are downloaded by ultralytics.

This is an engineering demonstration built and validated in simulation. It is designed as a GAMP 5 Category 4 (configured product) pattern — thresholds derived from a frozen validation split, engine identity pinned by SHA-256 into the thresholds file and every audit record, fail-closed behaviour on late or slow verdicts, deterministic lockstep replays, a drift gate before any model change, and a parity audit against the previous baseline. That is a design pattern claim, not a certification: no regulatory approval, audit or certification of any kind is claimed or implied.
